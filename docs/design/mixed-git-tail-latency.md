# 混合任务 Git 尾延迟设计（0.6.5）

状态：已完成。固定前序和分段数据见[0.6.5 验证](../verification/0.6.5-fixed-load.md)。
IO 候选未达门槛，继续复用官方与 Default；发布默认关闭的分段观测能力。
用户开启计时后的[生产分段复测](../verification/0.6.5-production-phases.md)已完成：
较大的慢样本主要落在提供方区间，首段排队很小；未覆盖成本需进一步细分。
下文保留先设计、后实验的门槛与决策依据。

## 问题与假设

0.6.4 生产混合轮测中 Git P50/P95 为 idea-java 67/103 ms、官方 62.5/69 ms；
分任务复测为 62/83、64/85 ms。原轮换虽然让双方各先执行一半，但没有保证前一个
查询类型相同，不能据此把差异归因于插件或调度器。当前生产是单 Git 根，不启用多根并行。

保持完整查询、顺序、计数、过滤、分支与错误语义，不缓存状态、不延迟后再取样、
不缩小调用树或 Git 范围、不变更用户仓库映射与业务服务。查询共享 20 秒等待预算。

## 固定前序负载

为每个被测 Git 样本独立执行完全相同的前序查询并等待其完整返回，再立即发 Git 请求。
不能只在一对样本之前执行一次前序查询。生产前序为完整 14 节点 Arguments.required
入向树（depth=1/maxChildren=200/maxNodes=10000/timeout=10000），固定同一个
提供方；分别以官方或 idea-java 作为前序提供方，单独报告，不混合统计。
另测无前序对照。被测 Git 参数相同：includeUntracked=true、includeIgnored=false、
limit=10000，全部仓库和条目；不指定路径选择器。

双方顺序由独立轮次奇偶决定，每任务每方至少 80 次、各先执行 40 次，预热单列。
三方沙盒（官方同层、当前适配器、IO 候选）使用完整六种排列的 14 次循环，即每方
84 个正式样本，每个位置各 28 次、任意两方互相先执行各 42 次；两轮分别预热。
每个样本核对完整 MCP 文本与结构化结果，保留数组顺序；超时、截断或结果变化均显式报告，
不能悄悄删除慢样本。固定工作负载和正式测试期间不改源码，不并行运行构建和其他基准。

## 分段计时与归因

当前已安装 0.6.4 没有服务端分段观测接口，只能实测 Codex 端到端；不能从两次独立
请求之差推算服务端阶段。先保存该版本固定前序的生产基线，再在独立 IDEA 沙盒中插桩：

- 客户端：发送到完整响应，记录前序查询耗时、样本顺序和 GC 计数/暂停时间增量。
- HTTP/RPC：解析/校验、prepare 元数据、执行/序列化；使用测试包装记录，不输出认证头或参数。
- 适配器：当前可用性与 schema、Git 范围检查、协程提交到进入提供方、提供方与结果转换。
- Git：优先使用 SDK 的公开命令监听事件观测开始/结束，不记录命令行、环境或输出。
  无可用公开边界时，只在测试中对真实 SDK 方法作探针，明确未测到的边界，不把估算当实测。

阶段使用单调时钟；客户端以轮次和位置关联各自响应头，跨线程显式传播请求计时上下文，
不依赖 ThreadLocal 隐式跨协程传播。
并发或嵌套阶段不能简单相加；报告覆盖范围与残差。生产分段观测若需要新插件，
本轮先完成沙盒测量与交付，不声称用户已安装新版本。

观测实现选择：增加默认关闭的 `dev.ideamcp.timings` 开关，认证成功后才建立请求内
计时上下文；在 HTTP `Server-Timing` 头中返回固定阶段名与耗时，不返回参数、路径、
令牌、命令行或业务输出，不落日志。通过协程 ThreadContextElement 显式传播上下文，
避免 ThreadLocal 不能跨调度的问题。嵌套总时间单独命名；响应头只覆盖序列化以前的
阶段，不假称包含之后的发送时间。客户端总耗时减去服务端非重叠阶段作为传输/排队
等未覆盖成本的合计，不能再细分成未实测的网络或队列。

Git 没有公开的全局命令计时订阅口时，在独立测试中用 Git 服务代理给真实命令处理器
添加公开 GitLineHandlerListener；只计 STATUS 开始/结束。命令识别若需私有访问，仅在
测试使用；代理不进入发布包。Default/IO 调度作为对照候选，未达门槛不启用 IO。

## 候选与安全边界

重点验证 Git 阻塞命令是否占用/排队在共享 Dispatchers.Default，以及元数据/范围检查
或 HTTP 输出是否产生尾延迟。候选为对真实官方 Git 工具使用适合阻塞工作的执行上下文，
或在公共 API 边界减少经实测证明的重复工作。任何上下文调整都必须保留 McpCallInfo、
工具筛选、路由、当前 schema、超时和取消；不得改变全局协程池或 HTTP 系统属性。
不使用生产反射、不替换 Git 解析器、不关闭校验、不用吞掉错误或隐藏结果获得速度。

采纳门槛：完整结果一致，至少两次独立预热的受控复测；中位数改善至少 20% 且 2 ms，
或目标 P95 改善至少 20% 且 5 ms（尾延迟任务的明确收益），且中位数不恶化超过 5%、
无前序与多根基线 P95 不恶化超过 10%。不得事后改门槛或以人为注入饱和证明生产收益。
若仅在合成饱和场景受益，保留实验并如实说明，不默认启用。
