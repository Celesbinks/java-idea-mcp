# Git 命令与 HTTP 完成边界观测设计（0.6.6）

状态：已完成，[实验与交付记录](../verification/0.6.6-command-http.md)。
扩展 HTTP 完成观测及沙盒命令/等待诊断；执行候选没有明确收益，保留官方路径。
下文保留先固定方案、再实现观测与筛选候选的边界。
基线为[0.6.5 生产分段复测](../verification/0.6.5-production-phases.md)：
最大 177.605 ms 请求的提供方为 159.904 ms，首段排队 0.064 ms；
固定前序组未覆盖成本 P95 约 17 ms。两者不能直接命名为 Git 进程与网络耗时。

## 保持的语义

完整读取相同项目全部 Git 根和条目，保留官方命令、解析、分支、过滤、计数、排序、
截断、错误、取消与 20 秒预算；不跨请求缓存，不减少前序调用树或 Git 范围。
不替换生产 Git 服务、不注入生产反射或代理，不修改 IDE 全局协程池/HTTP 系统属性。
业务 Run/Debug 与用户仓库映射不参与实验。源码版本、已安装版本和沙盒版本分别报告。

## 观测层次

### HTTP：从任务提交到响应关闭

扩展默认关闭的 dev.ideamcp.timings。计时关闭时使用原执行器，无额外任务包装。
开启时仅保留线程局部的单调时钟数值：任务提交、任务开始、handler 进入。
认证和协议头校验成功后才把固定阶段写入请求上下文；认证失败不返回计时信息。
新增阶段区分 http_executor_wait、http_task_to_handler、http_admission。
前两项包含 JDK 任务调度及进入 handler 前处理，不将其混称为网络。
必须检查当前 JDK 实现的任务与 handler 对应关系，并验证复用线程/连接时无残留。

响应头在发送前生成，不能携带本次之后才完成的发送计时。开启计时时增加仅由插件
生成的数值请求序号响应头，与可选的 JFR 自定义 HttpRequestCompleted 事件关联。
事件仅含序号、固定阶段耗时和成功/失败标志，不含 JSON-RPC id、工具名、路径、
参数、输出、凭据、请求头或启动命令。默认不主动开启 JFR 录制、不落日志或磁盘。
仅在相应 JFR 事件被显式启用时提交事件；关闭计时则无计时头和完成事件。

完成事件记录构造响应头、sendResponseHeaders、正文写入、exchange.close 与整个
handler/任务区间；原有解析/RPC/序列化仍来自请求上下文。发送异常也关闭 exchange，
完成状态区分成功与失败；不吞异常、不更改原有 HTTP/MCP 正文和状态。
单次事件中的总量与子阶段重叠，不能全部相加。
客户端分开记录 POST、响应头/首字节、完整正文、JSON/SSE 解析；使用请求序号关联，
不对齐两台时钟的绝对时间。服务端 close 可能晚于客户端收完，残差不强制归零。

### Git：独立沙盒的真实官方调用

沿用测试专用 Git 服务代理和真实 GitLineHandlerListener，命令识别反射仅在测试。
记录 runCommand 进入、processStarted、processTerminated/startFailed、runCommand 返回：
git_command_total、git_before_process、git_process、git_after_process 和命令次数。
命令事件可能在不同线程回调，显式传递请求上下文并保证完成只记一次。
没有 processStarted/terminated 时阶段缺失，不能用 0 伪装已测到。
processStarted 到 processTerminated 包含进程生命周期与 IDE 输出/回调交接，不能称为
操作系统 CPU 时间或仅 Process.waitFor。另记录调用线程 CPU 与 GC 增量，
CPU 差值不能直接命名为锁或进程等待。需要更深锁/调度归因时单独诊断，不混入竞速。
诊断轮次仅在沙盒另启 ThreadPark/JavaMonitorWait/JavaMonitorEnter 与 GC 事件，
通过测试专用 GitCommand 的请求序号、线程和区间关联 waitForProcess 栈上的阻塞。
这表示调用线程等待进程处理器的时间，不等同于操作系统进程 CPU 或全部进程生命周期。

## 实验与候选采纳

先做真实安装 0.6.5 的同客户端分头/正文读取诊断，再在独立 262.10968.63 沙盒中
关联完整 HTTP 与 Git 阶段。使用相同完整 Arguments.required 入向树作为每个样本
独立的前序，并保留无前序对照。每次均比较整个 MCP 结果和完整性。

三方官方同层/原适配器/候选通过同一 HTTP 客户端和服务端边界比较；每轮每条件每方
84 次，六种排列各 14 次，每个位置 28 次，每一对先后各 42 次；两轮独立预热。
结果/范围改变或错误时停止并保留实验，不删除慢样本；诊断录制单独标注。
观测默认开关额外做 80 对对照，JFR 仅自定义事件录制，不采集用户启动参数。

三方性能控制具体为官方提供方经当前 HTTP、当前适配器经当前 HTTP、当前适配器经
0.6.5 HTTP 边界；旧 HTTP 类从原 ZIP 的 JAR 以隔离类加载器加载，其他提供方/计时类相同。
它用于检查扩展观测成本，不冒充整个旧插件与新插件的生产安装对照。
初步客户端分段显示 Node 原生 HTTP 的未覆盖 P95 约 1 ms，早先 fetch 客户端约 17 ms；
因此追加同一轮次 fetch/原生 HTTP 的平衡对照，固定同一个官方原生 HTTP 前序，
在相同完整结果下验证客户端路径差异。跨轮次的初步差异不先当作因果结论。

候选以阶段证据选择：只有实测出重复命令/等待或可避免的发送成本才改变执行路径。
不为了获得安装包强行替换 Git 实现或 HTTP 栈。JDK 的 TCP_NODELAY 全局开关可在
独立 JVM 中用于诊断，不能作为插件修改整个 IDEA 的方案。

沿用门槛：两轮 P50 改善至少 20% 且 2 ms，或目标 P95 改善至少 20% 且 5 ms；
P50 不恶化超过 5%，无前序与多根基线 P95 不恶化超过 10%。完整语义、取消和安全检查
先通过再讨论收益；不达标就保留原实现并说明观测价值及限制。
