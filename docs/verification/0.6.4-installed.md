## 实测结果

单位 ms，均为每任务每方 80 次。

| 混合轮测 | idea-java P50 / P95 / max | 官方 MCP P50 / P95 / max |
| --- | --- | --- |
| 调用树，14 节点 | 530 / 607 / 638 | 576 / 652 / 708 |
| Git，49 项 | 67 / 103 / 126 | 62.5 / 69 / 90 |

| 分任务独立复测 | idea-java P50 / P95 / max | 官方 MCP P50 / P95 / max |
| --- | --- | --- |
| 调用树，14 节点 | 561 / 629 / 637 | 581 / 645 / 666 |
| Git，49 项 | 62 / 83 / 90 | 64 / 85 / 93 |

分任务复测中，idea-java 的调用树中位数低约 **3.4%**、P95 低约 **2.5%**；
Git 中位数低约 **3.1%**、P95 低约 **2.4%**。均不足以宣称明显提速。
调用树在 0.6.4 中继续复用官方实现，不能把这点差异归因于新的调用树算法。

首轮混合 Git 的 P95 则比官方高约 **49.3%**。按先后分组（每组 40 样本）观察：

| Git 在一对中的位置 | idea-java P50 / P95 | 官方 P50 / P95 |
| --- | --- | --- |
| 先执行 | 71 / 121 | 62 / 68 |
| 后执行 | 60.5 / 77 | 63 / 72 |

首轮虽然双方各先执行一半，但任务轮换与提供方轮换仍会影响各自前一个任务的种类；
先执行的 idea-java Git 在该序列中紧随调用树，双方的前序负载并不完全相同。
这是追加分任务复测的原因。该现象与前序负载或调度影响相容，不能仅据此证明具体原因。
分任务复测的尾延迟差异缩小，但首轮波动仍是实际观察，不能宣称混合负载尾延迟已解决。

## 解释与后续方向

- 自动连接、版本、目录及原生/官方路由实际调用均正常，无需重新配置。
- 当前仅一个 Git 仓库，0.6.4 的 **2～4 个独立根并行调度不会启用**；当前表现符合
  单仓库继续复用官方路径的设计，不能把此前四仓库沙盒约 64% 的收益用于本项目。
- 调用树没有发现可靠的大幅收益；继续保留完整候选解析、歧义与树展开语义。
- 若继续定位混合任务尾延迟，应固定前序负载、记录 SDK 查询与 HTTP 端到端分段，
  检查调度和 GC 的相关性；现有毫秒样本不足以定位到具体线程或函数，暂不据此改代码。
- 此次仅连接与性能复验，更新文档；不改实现、不增加版本、不重建安装包或重跑沙盒。
  发布包的 87 项 JUnit、94 项协议/HTTP 断言和沙盒检查见[发布验证](0.6.4-query-performance.md)。

原始证据位于忽略目录 `build/benchmarks/064-production/`：connection.json（不含凭据）、
