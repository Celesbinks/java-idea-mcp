# 0.6.4 调用树与 Git 性能验证

日期：2026-10-24。先完成[设计](../design/call-tree-and-git-performance.md)，再实验、实现、差分和发布验证。

本文记录发布时的沙盒与旧版本生产基线；用户随后安装 0.6.4 的连接和生产结果见
[安装后复验](0.6.4-installed.md)，不能将下面的旧版本状态视为当前状态。

## 结论与交付

- 采用多仓库调度优化：2～4 个项目内、互不包含的 Git 根并行查询，最多四个后台工作线程。
  每个状态仍来自当前真实官方工具，保留全部计数、条目顺序、过滤、分支和 limit 语义。
  四仓库 HTTP 复测中位数改善 **64.3%**，P95 改善 **64.6%**。
- 不采用二进制 Git 输出处理器替换：多轮实验未达到 20% 且 2 ms 的收益门槛。
- 调用树保留官方实现：主要成本发生在层次展开之前，省略符号候选搜索可能改变歧义和多语言语义。
  没有把减少深度、返回节点或依赖范围包装为优化。
- 源码和安装包为 **0.6.4**；发布测量时本机安装服务为 **0.6.3**，initialize 已核对。
  当时 Codex 发现 idea-java **77** 项、官方 JetBrains **56** 项工具；后续生产耗时见安装后复验。

## 公平性与结果完整性

环境为 IDEA 2026.2.3 / IU-262.10968.63、JBR / JDK 25、Java 21 字节码，Gradle 9.1.0。
每个正式任务每方 **80 次**，预热 3 轮；轮次奇偶决定提供方先后，双方各先执行 40 次。
任务轮换与提供方顺序独立；不并发执行两个被比较的方案。P50 采用中间两项平均，
P95/P99 采用 nearest-rank；80 个样本的 P99 就是最大值，不能据此声称总体 P99 已稳定。

生产测量通过当前 Codex 的两个真实 MCP 连接。沙盒比较在同一 IDE JVM 中调用真实官方
提供方与新适配器，分别给出同层直接调用和相同 HTTP / JSON-RPC 封装结果；
没有把沙盒 SDK 数据当作已安装 0.6.4 的 Codex 端到端数据。

每次比较完整 JSON / 文本，JSON 对象字段次序可忽略，数组顺序保留。
调用树包括全部 14 节点及其签名、位置、树路径和 usage 信息；拒绝超时或省略行。
生产 Git 状态测量时为完整 47 项，limit=10000、includeUntracked=true、includeIgnored=false。
源码树测量前后的路径和 SHA-256 清单完全相同。报告本身和后续版本修改发生在测量之后。

## 已安装 0.6.3 的生产基线

单位 ms；每项每方 80 次，正式 320 次调用、含预热 332 次完整结果校验。

| 相同任务与完整范围 | idea-java P50 / P95 / max | 官方 MCP P50 / P95 / max |
| --- | --- | --- |
| Arguments.required 入向调用树，depth=1、maxChildren=200、maxNodes=10000，14 节点 | 506 / 578 / 599 | 478 / 583 / 616 |
| Git 状态，1 仓库、完整 47 项 | 61 / 74 / 119 | 68 / 75 / 86 |

这是旧版本的最新基线，不是 0.6.4 优化后的生产结果。单仓库的中位数差异未达采纳门槛，
idea-java 最大值也更高，不能据此宣称单仓库提速或尾延迟已解决。

为定位调用树而额外测量 depth=0（仅根节点），每方 20 次、预热 2 轮：
idea-java P50/P95 为 529.5/607，官方为 496/588。它与完整树属于不同范围，
只用于阶段定位，不计入速度改善率。两组耗时接近，表明当前项目中展开 13 个子节点
不是主要成本；不能将两次独立测量简单相减作为精确阶段时间。

## 调用树阶段定位与未采用的候选

测试将项目主源码复制到临时项目，使用真实 JDK 和 IDEA 索引。
通过仅限测试的反射分别调用 SDK 目标解析阶段与完整分析器，各 80 次：

| 沙盒阶段 | P50 | P95 | max |
| --- | ---: | ---: | ---: |
| 目标解析 | 37.77 | 55.04 | 63.97 |
| 完整 14 节点树 | 43.58 | 69.26 | 86.52 |

目标解析中位数约占完整分析的 87%。沙盒没有复制生产项目全部 446 个依赖，
绝对值不能外推到生产；生产仅根节点探针提供了独立的方向性证据。
SDK 会合并 QualifiedNameProvider、ChooseByName 符号候选及所属类型中的可调用对象等结果。
直接使用 Java 精确解析替代或省略搜索会遗漏歧义、多语言或库中的候选；没有稳定公共 API
可向当前私有分析器注入完全等价的候选结果。因此不加入生产反射、跨请求缓存或自制简化调用树。
后续应优先推动 SDK 提供可剖析、可并行的候选收集边界，再做完整歧义与跨语言差分。

Git 相同临时仓库、相同 porcelain -z 参数、复用 SDK 解析器的最终进程实验：

| 处理器 | P50 | P95 | max |
| --- | ---: | ---: | ---: |
| 官方 GitLineHandler | 46.18 | 50.03 | 54.19 |
| GitBinaryHandler 候选 | 46.36 | 49.41 | 50.92 |

此前两轮也未达门槛。二进制读取不能解决这次瓶颈；多仓库串行累计的外部命令成本才是
有明确优化空间的部分。进程实验未直接剥离操作系统进程创建、Git 扫描及 SDK 环境准备的单独成本。

## 0.6.4 多仓库优化复测

四个独立临时 Git 仓库，三个包含暂存与未暂存修改、中文/空格重命名、未跟踪及忽略项，
另一个为干净仓库。完整查询 limit=10000，包含未跟踪和忽略项；每轮比较完整官方输出。

| 同层直接 SDK / 适配器 | idea-java P50 / P95 / max | 官方 P50 / P95 / max |
| --- | --- | --- |
| 第一次 80 对 | 70.96 / 76.80 / 83.42 | 199.53 / 222.35 / 238.60 |
| 独立预热后的第二次 80 对 | 68.82 / 75.61 / 80.61 | 189.26 / 229.87 / 248.79 |

独立预热复测不是另一台机器的跨环境实验。相同 HTTP / JSON-RPC 封装的正式结果：

| 完整 HTTP 任务，各 80 对 | idea-java P50 / P95 / max | 官方 SDK 同封装 P50 / P95 / max |
| --- | --- | --- |
| 四仓库 | 73.04 / 80.78 / 86.85 | 204.65 / 228.10 / 238.20 |
| 单仓库回退 | 54.23 / 59.03 / 68.63 | 54.49 / 58.95 / 59.67 |

四仓库达到中位数至少 20% 且 2 ms、P95 不恶化超过 10% 的门槛。
单仓库中位数基本相同，P95 约增加 0.13%；最大值仍存在波动，没有承诺 P99 改善。
工作线程全局上限四个；任务排队计入同一个 20 秒预算。根、对象身份和分支在前后校验，
子结果分支也必须匹配起始快照；不缓存文件状态。任何子错误都不返回部分仓库列表。

显式选根、单根、嵌套根、项目外根、超过四根、符号链接和不支持的参数组合保留官方路径。
官方不支持 includeIgnored=true 且 includeUntracked=false，新代码直接回退并保留原错误。
路由 execute_tool 内部的 Git 调用仍由 SDK 负责；不改变用户的工具禁用与路由设置。
