# 0.6.1 速度对比：相同任务和完整结果范围

日期：2026-10-24（Asia/Shanghai）。本机 Windows、IDEA 2026.2.3 / IU-262.10968.63、运行中的 Java Symbol MCP **0.6.1**、ripgrep 15.2.0。IDEA 已启动、索引就绪，Codex 已发现 77 项 idea-java 工具。

结论：在这四项等价任务中，idea-java 与官方 JetBrains MCP 的中位数相差 **0～1 ms**。单次独立 Shell 工具调用明显较慢；常驻 Shell 内的查询体则很快，尤其文件枚举。优先优化文件枚举及批量执行，不宜为了不足 1 ms 的适配开销重写全部官方能力。

## 方法与结果一致性

- 搜索范围固定为 `src/main/java/**`、`src/test/java/**` 下的全部 Java 文件，共 **46 个、319935 字节**。读取任务固定为 `src/main/java/dev/ideamcp/protocol/Arguments.java` 的完整内容。
- 三方分别为当前 Codex 的 `idea-java`、当前 Codex 的官方 `jetbrains`，以及 `exec_command` 中执行 PowerShell / rg。主表衡量从调用 `tools.*` 到取得返回值的耗时，计时器分辨率 1 ms。
- 两轮预热后各测 20 轮，任务顺序轮换，提供方顺序使用六种排列，全部串行。四项三方任务共 **240 次正式工具调用**；补充诊断共 60 次，均无错误。预热另计，不混入统计。
- 每次测量后校验完整结果。仅统一路径分隔符、排序和结构，不删命中、不只取首项、不用减少分页大小提速。命中坐标为 1-based UTF-16，范围终点右开；rg 的 UTF-8 字节偏移转换为同样的 UTF-16 列。
- 固定结果为：读取 **39 行**（包含末尾空行）、文本 **15 处**、正则 **90 处**、文件 **46 个**。搜索上限 1000，实际未截断、无 partial/more；读取上限 5000，完整返回该短文件。
- 预检发现官方 `read_file` 的较小 limit 会截断中间内容，因此正式任务改为读取完整短文件，避免拿截断结果比较。
- 开始和结束的全部源码 SHA-256 指纹一致；同一 Shell 的另 80 次查询也逐项与同一完整结果校验通过。
- 没有启动/重启服务、改断点、执行 SQL 或读取业务日志/调试变量。没有强制保存用户文件或修改生产源码。

## 三方完整工具调用耗时

单位：**毫秒，中位数 / P95**。P95 使用最近秩法，即 20 个样本排序后的第 19 项。MCP 的这四项 API 均为同名工具；idea-java 走官方适配器。

| 相同任务 | idea-java 0.6.1 | 官方 JetBrains MCP | 不使用 MCP：每次独立 Shell |
| --- | ---: | ---: | ---: |
| 完整读取 Arguments.java，39 行 | **7.5 / 11** | **7 / 9** | 664.5 / 697 |
| 精确文本 TokenStore，15 处 | **16 / 19** | **16 / 19** | 698 / 716 |
| class 声明文本模式，90 处 | **23 / 25** | **22 / 27** | 704.5 / 728 |
| 全部 Java 文件枚举，46 个 | **184 / 227** | **183 / 212** | 685 / 716 |

文本模式为字面量 `TokenStore`；正则为 `\bclass[ \t]+[A-Za-z_$][A-Za-z0-9_$]*`。后者明确是文本模式，包括字符串/注释中符合模式的文本，不是 Java 类符号解析。

每次单独启动的 Shell 大量耗时来自 Shell 启动、JIT、执行工具调度和序列化等。不能把约 665～705 ms 全部算成 rg 的算法耗时，也不能据此声称 MCP 在所有情况下都比本地查询快。

## Shell 查询体与批量复用

这里测量查询体：包含文件读取或 rg 子进程、结果解析和坐标转换，排除外层工具调度、Shell 启动和最终 JSON 序列化。同一 Shell 仍为每项搜索/枚举启动 rg，没有把答案缓存为常量。

下表与主表属于不同计时层，不能直接当作同一端到端指标。它回答的是“复用一个 Shell 后，实际查询还需多久”。

| 任务 | 独立 Shell 内查询体，中位数 | 同一 Shell 连续查询，中位数 / P95 |
| --- | ---: | ---: |
| 完整文件读取 | 10.650 | **0.191 / 0.217** |
| 文本搜索 | 49.253 | **16.149 / 17.285** |
| 正则搜索 | 54.249 | **22.408 / 30.779** |
| 文件枚举 | 26.496 | **13.235 / 14.426** |

因此，一次交互式查询可优先用已经连接的 MCP；大量纯文件/文本任务可以合并到一次命令中摊薄启动成本。当前尤其值得研究文件枚举：同结果范围下，MCP 约 183～184 ms，同一 Shell 内 rg 约 13 ms。后者尚不构成“已实现一个更快的 IDE 原生替代”的证据。

## 优化建议与顺序

1. **先优化文件枚举。** 针对 `search_file` 做剖析，研究更早应用 paths、使用已有 IDE 索引、避免遍历无关根的原型。保证内容根、忽略/排除规则、glob、取消和完整分页仍等价；再用本次脚本复测。不能直接用只识别磁盘文件的 rg 取代全部 IDE 文件语义。
2. **调用侧合并纯文件操作。** 连续的读取、文本搜索、文件枚举尽量合并到一次 Shell 作业；保留 MCP 用于交互式查询及需要 IDE 语义的操作。不要为每个很小的文本任务新开一次 Shell。
3. **继续复用官方能力。** 本次适配器的中位数增量为 0～1 ms，没有证明全面独立开发更划算。原生诊断只改善约 1.3%，也不足以触发既定替代门槛：相同结果、中位数至少改善 20% 且至少 2 ms，P95 回退不超过 10%。
4. **目录/schema 优化排在后面。** 源码中 RpcHandler 为扩展工具取得完整目录，IdeaToolBackend 又构建提供方目录，OfficialMcpAdapter 随后再次定位工具并构建目标 schema。可以传递请求内的已验证描述或缓存不可变 schema / 名称映射，减少重复构建。但动态插件、工具禁用、路由模式和确认规则必须立即生效；当前实测增量很小，不把这当作已证实的主要瓶颈。
5. **减少结果重复呈现，保持范围完整。** 本次正则查询两种 MCP 的工具结果 JSON 表示均为 25506 字符，Shell 返回约 11295 字符；MCP 的 content / structuredContent 有重复。客户端优先消费结构化结果、避免给模型重复展开两份内容。此数字不是网络字节或模型 token，也未测模型阅读/推理耗时。

若进一步优化 PSI 查询，按 [JetBrains PSI Performance](https://plugins.jetbrains.com/docs/intellij/psi-performance.html) 检查重复计算、意外 AST 加载及缓存依赖；缓存不能忽略索引状态和源码变化。这里属于后续建议，本轮未修改实现来追求基准成绩。

## 证据与限制

本轮不复用上一轮类名/调用者的非等价范围数据。这里的三方等价结果仅覆盖纯文件/文本任务；不将文本命中描述为符号、定义或调用关系。MCP 主表比较的是工具调用体验；Shell 查询体表用于解释批量复用，不能混为算法基准。未计模型推理、阅读、规划、首次 IDE 启动和冷索引成本；20 个样本不足以给出跨机器显著性结论。

当前项目仅 46 个 Java 文件，结果不能外推到大型单体仓库、远程文件系统或大型返回值。建议在小/中/大项目及冷/热状态分别重复相同完整性校验，再决定默认路径。

可复核产物位于已忽略目录 `build/benchmarks/061-equal-scope/`：

- `raw-results.json`：300 次正式工具调用、每次结果校验及 Shell 批量查询的精简样本。
- `summary.csv`：中位数、P95、最小/最大值。
- `expected.json`：三方共同的完整规范化结果。
- `shell-baseline.ps1`：单次及常驻 Shell 内批量基线。
- `runner.js`：Codex functions.exec 测量器；仅在相同工具宿主内运行。
- `shell-batch.json`：80 次批量查询完整结果。
- `source-before.json` / `source-after.json`：源码长度及 SHA-256，前后一致。

## English summary

With identical scopes and fully validated results, idea-java 0.6.1 and official JetBrains MCP have median latencies within 0–1 ms across file reading, literal search, regex search and file enumeration. Each case used two warm-up rounds and twenty measured samples per provider, in rotated serial order. All 300 measured tool calls passed, and the 46-file source snapshot stayed unchanged.

Per-call Shell timings include startup and tool dispatch; batched query-body timings exclude those layers and are reported separately. File enumeration is the clearest optimization candidate: about 183–184 ms through either MCP versus about 13 ms inside a reused Shell. Native IDEA diagnostics improved only about 1.3% on a clean file; no false Shell equivalent is supplied. Prioritize scoped enumeration and batching, retain official reuse until an equivalent native replacement meets the performance gate, and preserve dynamic filtering, cancellation and cache invalidation. These are local warm-state measurements, not cold-index, large-repository or model-reasoning benchmarks.
