## 结论

- 安装服务 **0.6.5**、官方服务 **2026.2.3**，协议均为 **2025-11-25**。
  idea-java 的每个正式 HTTP Git 响应都有完整预期计时字段；官方响应没有这些字段。
- 当前 Codex 与同客户端 HTTP 对照分别取样，不混合统计。
  HTTP 两轮每条件每方 80 次，未显示跨所有条件稳定的提速；双方完整结果始终一致。
- 最大 177.605 ms 慢样本中，adapter_provider_total=159.904 ms、首段排队仅 0.064 ms。
  第二轮无前序也有 135.742/126.198 ms（客户端/提供方）的慢样本。
  **较大的慢样本主要落在官方提供方调用区间，首段协程排队不是本轮主要耗时。**
- 仍有未覆盖成本：固定前序组的 P95 约 16.8～17.3 ms。不能把它全部称为网络、
  HTTP 队列或 IDE 内部耗时，也不能把 provider_total 全部称为 Git 子进程耗时。
- 两个完整实验含预热共 **2490 次完整 MCP 结果校验全部一致**；
  最初未完成的 HTTP 实验返回一次官方 404，单独保留并排除于上述完整实验。
  本轮没有新增优化实现或重打插件包，继续使用现有 Default 与官方 Git 路径。

## 分段归因

生产只提供 HTTP/RPC 与适配器边界，**不包含**沙盒专用 git_process、
git_command_total、git_handler。adapter_dispatch 为提交到首次进入协程的时间；
adapter_provider_total 从进入提供方调用到返回，包含官方内部后续挂起、
排队、锁/进程等待、解析以及回到调用方的交接，并非纯 CPU 或纯 Git 进程时间。

单仓库下可用的非重叠覆盖时间为：

`covered = http_read + http_parse + rpc_total + http_serialize`

`其他服务端 = covered - adapter_provider_total`

`未覆盖 = 客户端总耗时 - covered`

其他服务端包含首段排队、元数据、校验、范围判断、结果转换及序列化等；
首段排队已经包含在其中。未覆盖合并了计时开始前的处理、认证、头部构造/发送、
传输、连接和客户端接收/解析/调度等成本，当前接口不能进一步分离。
嵌套的 *_total 不能全部相加；以下各列的 P95 来自独立分布，不能做分位数相减来归因。

## 优化建议与采纳顺序

1. **先细分提供方内部边界。** 在独立沙盒沿用真实官方 Git 命令，
   对齐 git_command_total / git_process 与 provider_total，并关联 GC/调度事件。
   生产侧可以在相同固定负载下做独立的 IDEA CPU/JFR 诊断轮次。
   JetBrains 建议在性能采样期间反复复现相同问题；
   JDK 25 的 profile JFR 配置比 default 收集更多信息、开销也更高，
   因此诊断样本与公平竞速样本分开，不混入上述时间表。
   参考 [JetBrains 性能采样说明](https://intellij-support.jetbrains.com/hc/en-us/articles/207241235-Reporting-performance-problems)
   与 [JDK 25 jcmd/JFR 文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html)。
   若计时确认重复命令或可避免的串行等待，再设计请求内复用或调度改动，
   保持实时状态、过滤、计数、分支、顺序、错误与取消语义。
2. **单独细分未覆盖成本。** 在受控诊断客户端记录响应头到达、完整响应接收、
   JSON/SSE 解析完成的时间；服务端诊断包装记录 handler 进入、认证结束、
   响应发送边界。所有记录只含请求序号和固定阶段数值。
   body 写入完成发生在响应头之后，不能伪装成已经测到的同一 Server-Timing 字段。
   先确定这约 17 ms 的 P95 分量在哪一侧，再考虑连接复用、响应发送或客户端读取改动。
3. **继续保留 Default 与官方 Git 路径。** 当前首段排队只有几十微秒；
   provider_total 仍包含内部调度，尚不能排除它，但整体切 IO 缺乏收益证据，
   此前两轮沙盒候选也未通过门槛。路由、元数据与序列化的整个可节省范围较小，
   目前优先级低于提供方和未覆盖阶段。保持每次读取完整实时状态。
4. **实现候选仍使用既定门槛。** 两轮独立预热，完整结果一致，
   P50 改善至少 20% 且 2 ms，或目标 P95 改善至少 20% 且 5 ms，
   并满足无前序/多根基线退化限制。80 个样本的经验 P99 等于最大值，
   本轮没有可靠估计总体 P99，也未据此采纳新的运行优化。
